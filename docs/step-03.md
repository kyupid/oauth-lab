# 스텝 3 — 공격 #1: state 없는 CSRF (세션 고정), 그리고 방어

## 공격: 피해자를 공격자 계정에 로그인시키기

`make attacker` 로 :9003 을 띄운다. 시나리오:

1. 공격자(bob)가 먼저 정상 로그인해 **자기 계정의 인가코드**를 하나 받아둔다 (token 으로 안 바꾸고 code 단계에서 멈춤).
2. 그 code 가 박힌 링크를 "무료 아이폰 당첨!" 페이지에 심어 피해자에게 보낸다.
3. 피해자가 누르면 피해자 브라우저가 `http://127.0.0.1:9002/callback?code=<bob의code>` 를 방문한다.
4. 앱은 state 를 확인하지 않으므로, **피해자 세션을 bob 계정에 묶는다.**
5. 피해자는 "로그인 완료" 화면을 보고 자기 계정인 줄 안다. 하지만 남기는 메모는 전부 bob 것.

## 방어 전 재현 (검증됨)

```
피해자 홈 화면의 /me:  { "sub": "bob", ... }
피해자 홈 화면의 /notes: { "owner": "bob", "notes": ["밥의 비밀 메모"] }
```

피해자가 자기 계정이라 믿는 세션의 실제 주인이 **bob** 이다. 공격 성립.

## 방어: state

- 로그인 시작(`/login`)에서 예측 불가능한 `state` 를 만들어 **브라우저 쿠키**(`oauth_state`)에 저장하고, 같은 값을 `/authorize` 에 실어 보낸다.
- 콜백(`/callback`)에서 **쿠키 값과 URL 로 돌아온 state 가 일치할 때만** code 를 받아들인다.
- 공격자는 피해자 브라우저의 `oauth_state` 쿠키 값을 알 수 없다. 그래서 자기 code 를 흘려보내도 state 가 안 맞아 막힌다.

```
① 공격 재시도  → HTTP 400  "잘못된 state — 내가 시작하지 않은 로그인입니다"
② 정상 로그인  → HTTP 200  로그인 완료
```

## 핵심

**state 는 기밀이 아니라 CSRF 방어다.** URL 에 평문으로 실려도 상관없다.
중요한 건 "예측 불가능" 과 "내 브라우저에만 있는 쿠키와 대조" 이지, 비밀로 유지하는 게 아니다.

`state` 가 막는 것은 **로그인 CSRF** 다: "이 콜백이 정말 내가 시작한 로그인의 결과인가?"
code 를 훔치는 공격(스텝 4)이나 code 가로채기(스텝 5, PKCE)와는 다른 층위의 방어다.
